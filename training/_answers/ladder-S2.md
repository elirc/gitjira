# S2 reference: labels expand/contract

## Locks you need to know (Postgres 16)

| Statement                                | Lock on `Issue`                                                 | Notes                                                                                                                   |
| ---------------------------------------- | --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `CREATE TABLE "Label"` / `"IssueLabel"`  | none on Issue                                                   | FK creation _on the new table_ locks the referenced table briefly (SHARE ROW EXCLUSIVE)                                 |
| `ADD COLUMN x INT NULL` (no default)     | ACCESS EXCLUSIVE, metadata only                                 | instant, but it **waits** behind long transactions, and everything queues behind it. That's why you need `lock_timeout` |
| `CREATE INDEX`                           | SHARE, which blocks writes for the whole build                  | what `20260710000000_perf_indexes` did                                                                                  |
| `CREATE INDEX CONCURRENTLY`              | SHARE UPDATE EXCLUSIVE                                          | writes continue; can't run in a transaction block; can leave an INVALID index on failure                                |
| `ADD CONSTRAINT … FOREIGN KEY`           | SHARE ROW EXCLUSIVE on both tables, plus a full validation scan |                                                                                                                         |
| `… NOT VALID` then `VALIDATE CONSTRAINT` | brief lock, then SHARE UPDATE EXCLUSIVE during validation       | the zero-downtime way                                                                                                   |
| `DROP COLUMN`                            | ACCESS EXCLUSIVE, metadata only                                 | instant, but breaks any code still selecting it (INC-003)                                                               |
| `ALTER COLUMN TYPE` (most)               | ACCESS EXCLUSIVE **plus a table rewrite**                       | what `20260709194359` did to `position`                                                                                 |

**Prisma runner:** `prisma migrate deploy` sends each migration file's SQL as one script. A multi-statement script executes in an implicit transaction, so `CREATE INDEX CONCURRENTLY` fails there ("cannot run inside a transaction block"). The widely used workaround is **one `CONCURRENTLY` statement alone in its own migration file**. Prove it on a scratch DB before you rely on it, and check that a failed concurrent build leaves an INVALID index you must drop before retrying. Prefix risky migrations with `SET lock_timeout = '1s';`, and accept that a timeout fails the release phase, which is the safe outcome: nothing rolls.

## Rename semantics

After R3/R4, a rename is `UPDATE "Label" SET name='frontend' WHERE id=…`: one row, instant for 2.1M issues. **During R2** (dual-write, reads still from `labels[]`), a rename would have to rewrite 2.1M arrays **and** stay consistent with concurrent issue writes that carry the old name. Disable the rename feature until R4.

## Dual-write cost and failure

Per issue write: plus 1–N label upserts plus a delete/insert on `IssueLabel`, all in the same transaction. A failure aborts the whole write, so the two representations can't diverge, at the cost of the new path failing the old feature. For the first days, consider a feature flag to disable dual-write without a deploy.

## Tests

- **N−1 compatibility:** run the previous release's API integration suite against the migrated schema in CI.
- **JQL parity:** for a seeded project, `label = x` via the array and via the join return identical ids for every label.
- **Backfill rerun:** run the job twice, and the counts are unchanged, with no duplicate `IssueLabel` rows.

## When not to do it

If the actual need is "rename fast plus count per label," a GIN index on `labels` (`CREATE INDEX CONCURRENTLY … USING GIN ("labels")`) makes `has` and per-label counts fast. A rename job can rewrite arrays in batches in the background (eventually consistent, minutes on 2.1M rows). That's one release, no contract phase. Colors could live in a small `LabelMeta(projectId, name, color)` table. Choose normalization when labels become entities: permissions, descriptions, analytics, cross-project.

## ADR 0031 vs history

ADR 0031 describes expand/contract with `position` as the example. The actual migration `20260709194359_issue_position_fractional` did the naive in-place `ALTER COLUMN … SET DATA TYPE TEXT`: a rewrite under ACCESS EXCLUSIVE. The policy was written after the fact, and nothing enforces it (INC-003's CI-check answer).
