# Sol: independent verification

This review records observable tests and failures only. I wrote contract-driven API tests in `tests/api.test.js` and a separate-process SQLite race in `tests/concurrency.test.js`. The test data uses temporary databases; no user database is touched. Both files passed `node --check` before the backend was present.

The API tests exercise demo sessions, the secure cookie attributes, project membership and guessed issue IDs, viewer write rejection, issue create/edit/archive, comments, activity, search and combined filters, invalid input, last-owner protection, stale-write conflict details, atomic rollback when an event insert is forced to fail, and reopening the same SQLite file. The concurrency test starts two `src/server.js` processes on the same SQLite file, issues two edits against one version, requires exactly one success and one 409, then restarts and reads the winner with the persisted session.

The first backend run passed 7 of 8 tests. The single failure was my test's assumption that a new issue would be `LAUNCH-1`; the product intentionally seeds nine LAUNCH issues, so the actual new key was `LAUNCH-10`. I changed the assertion to calculate the expected next number from the existing issues. This was a test error, not a backend defect. The next run passed 8 of 8.

At root's request, I expanded the suite to exact 409 handling for the last owner, expired sessions, malformed JSON, oversized bodies, stale archive attempts, new project ownership and key collisions, member removal with an already issued cookie, versioned unassignment on removal, rollback of member removal/create/edit/comment when activity insertion fails, and issue number reuse after a failed create. I also added simultaneous issue creation from two processes and required distinct consecutive project numbers. That run passed 11 of 11 tests.

Astra's separate backend audit found three genuine input bugs, documented in `journal/reviews/04-astra-backend.md`: NUL text could be truncated, array/object IDs could be accepted or crash validation, and the old 32 KB JSON limit rejected a valid 10,000-character escaped description. Root fixed the backend. I added regression requests for each behavior, including a body above the new 128 KB limit. The final `npm test` run passed **12 of 12 tests** in 5.1 seconds on this machine. The deliberate SQLite triggers produced expected `Request failed: forced activity failure` log lines; the HTTP requests failed and their writes were rolled back.

The strongest observed evidence is the two independent Node processes sharing one SQLite file: two same-version edits yielded one 200 and one 409, one update event, and the winner remained after both processes stopped and a fresh process reopened the database. Two simultaneous creates received distinct consecutive numbers. The API review found no additional defect after these fixes. Browser behavior is outside this review and is tested separately by root.
