# Sealed capstone and review notes

Reject a schema change that silently supplies update defaults, a merge that drops zero/null, or a client patch that converts every absent property into a clear. Require a persisted untouched-field assertion, not only a response-title check.

For the gate, look for cleanup on both resolve and reject, a controlled-overlap test, and a caller-identity boundary. A map of promises without eviction for failed work can become a permanent failure cache. A successful gate test is not a complete auth review: keep transport credentials, session transitions, and retry safety in the capstone's evidence limits.

## Assess a learner's explanation

Ask for the actual input and observable result, then change one assumption. A strong explanation adapts the test or identifies a missing product decision. A weak explanation repeats the reference implementation without explaining why its boundary belongs there.

Do not award runtime evidence for a written plan. Keep “source supports this,” “model reproduced this,” and “application reproduced this” as separate statements. If an existing implementation already handles a scenario, the useful contribution may be a test and a clearer contract rather than another fix.
